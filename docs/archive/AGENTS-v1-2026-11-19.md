## 一、项目定位（我的原话，AI 不要扩展）

2. **权限**：基于角色的权限控制（RBAC），区分管理员和普通用户能访问哪些接口
3. **智能对话 + 知识库**：用户可以发起对话，回答能引用知识库文档里的内容
4. **多智能体交互**：多个扮演不同角色的智能体协作，共同完成一次回答

目录按阶段逐步建：**没到的阶段，不要提前建空目录和空文件**，避免看一堆不知道干什么的层。
到哪个阶段再建哪块，建之前告诉我。

分层职责，不许越界：

- `api/`：收参数、校验、调 service、返回统一结构。**不写 SQL，不写业务判断。**
- `services/`：所有业务逻辑，数据库事务边界也在这里。
- `models/`：只放表结构，不放业务方法。
- `schemas/`：请求 / 响应结构。禁止把 ORM 对象直接返回给 api 层。
- `core/config.py`：配置集中管理，**任何地方禁止直接 `os.environ[...]`**。

## 四、可读性硬规则

- 函数不超过 **30 行**，嵌套不超过 **2 层**。
- 变量名用完整单词：`user_question`、`retrieved_chunks`、`order_total_price`；
  禁止 `data`、`res`、`tmp`、`x`、`ret`。
- 每个函数上方三行注释：

  ```python
  # 做什么：按条件分页查询用户列表
  # 入参：keyword 搜索关键词；page 页码；page_size 每页条数
  # 返回：用户列表和总数；无结果时返回空列表
  ```

- 复杂判断前加一行注释说明**为什么**，不写"给变量赋值"这种废话。
- 魔法数字 / 字符串一律提常量或枚举（超时秒数、top_k、模型名都算）。
- 参数写全名，禁止用 `*args` / `**kwargs` 传业务参数。

## 五、禁用写法

- 嵌套推导式；把推导式塞进函数调用的参数里。
- 一行多语句；三元表达式套三元表达式。
- 用装饰器承载业务逻辑（路由装饰器、依赖注入除外）。
- 吞异常：空 `except`、`except Exception: pass`、出错返回 None 装作没事。
- 不为 3 行逻辑抽基类 / 工厂 / 抽象层；抽象层级**最多两层**。
- 禁止顺手重构、顺手格式化、顺手改命名（diff 必须干净可审）。
- 禁止自行安装依赖；需要新包先报包名、用途、版本、体积，等我同意。
- 禁止读写 `.env`、密钥文件；破坏性命令（删文件、drop 表、`git reset --hard`）先问我。

## 六、LLM 专项规则（本项目适用：阶段三、阶段四）

> 阶段一（登录）、阶段二（权限）里不要碰模型相关的任何东西。
> 到阶段三我明确说了才开始建 `llm/` 和 `rag/`。

1. **模型调用集中在一处**：全部走 `app/llm/client.py`。
   禁止在 service 或 api 里自己拼 HTTP 请求、自己读 API Key。
2. **提示词集中管理**：全部放 `app/llm/prompts/`，按用途一个文件。
   禁止在业务代码里拼接几十行的长字符串。
3. **每次调用必须有**：超时时间、重试次数上限、失败时的降级返回。
   禁止让一个模型请求把接口挂死。
4. **流式输出统一封装**：只用一个 SSE 工具函数，禁止每个接口各写一套。
5. **日志禁止打印完整提示词和 Key**：只记录长度、模型名、耗时、token 用量，
   敏感内容截断显示。
6. **缓存 key 统一前缀**：按 `fengxuan:{模块}:{对象id}` 格式，**必须设 TTL**，
   禁止无过期时间的写入。
7. **如涉及知识库检索**：结果必须带原文片段和所属文档，前端能显示"引用自哪里"。
   本项目是否要做检索，以第一节为准；没写就不要做。
8. **能用代码判断的不要交给模型**：数值计算、权限判断、状态流转用代码写死，
   模型只负责语言理解和表达。这是为了稳定性和可调试性。
9. **模型输出必须校验**：结构化输出先做 schema 校验，解析失败要有明确报错，
   不要默认"模型一定按格式返回"。

## 七、数据库与缓存（MySQL 8 + SQLAlchemy 2.0）

### 连接与配置

- 连接串、池大小、超时全部写在 `core/config.py`，从 `.env` 读取，禁止硬编码。
- 连接串必须带 `charset=utf8mb4`，否则中文和 emoji 会乱码或截断。
- 建库时字符集必须 `utf8mb4`、排序规则 `utf8mb4_unicode_ci`，时区统一 `+08:00`。
- 连接池参数：`pool_size=5`、`max_overflow=10`、`pool_recycle=1800`，
  必须开 `pool_pre_ping=True`（防 MySQL 8 小时断连后第一次请求报错）。

### 写库规则

- 一律用 SQLAlchemy 2.0 写法（`select()` / `session.execute()`），
  禁止 `session.query()` 这类旧风格，禁止同一个文件里两种混着写。
- **禁止用 f-string 拼 SQL**，参数一律通过绑定传入（防注入，也确实好读）。
- 事务边界在 service 层：service 里 `with session.begin()`，
  **api 层永远不 commit**。
- 批量写入超过 100 条时用 `bulk_save_objects` 或分批提交，别一条一条循环 insert。
- 迁移文件一旦执行并提交，禁止修改，只能新增。

### 表设计约定（保持统一，别每张表一个风格）

- 表名用复数小写下划线：`users`、`knowledge_documents`、`chat_sessions`。
- 每张表必备四列：`id`（BIGINT 自增主键）、`created_at`、`updated_at`、
  `is_deleted`（TINYINT 默认 0，软删除）。
- 关联字段命名统一 `xxx_id`（如 `user_id`、`session_id`），不建物理外键，
  在 service 层校验存在性。
- 状态、类型这类字段用 TINYINT + 常量类（`class OrderStatus`），禁止裸数字 1/2/3。
- 金额用 `DECIMAL(12,2)`，禁止 FLOAT/DOUBLE。时间用 `DATETIME`，不要用字符串存时间。
- 需要存 JSON 的字段用 MySQL 原生 `JSON` 类型，不要塞一段字符串。
- 建表时给常用查询条件加索引，索引命名 `idx_表名_字段名`。

### 查询规则

- 列表查询**必须分页**，默认 `limit=20`，且必须限制最大值（如最大 100），
  禁止无 limit 的 `select()` 全表返回。
- 禁止在循环里查数据库（N+1）；需要关联数据时一次性查出来再在内存里组装。
- 单条查询用 `session.scalar()` / `session.scalars().first()`，不要查出来再 `[0]`。

### 缓存

- 缓存读写封装在 `utils/cache.py`，业务里不直接调客户端。
- 写入必须设 TTL，禁止无过期时间。

## 八、日志

## 十二、边写边学（本项目最重要的协作方式）

我不是要一个写完的代码库，我要在写的过程中学会。所以下面这些是硬流程，

### 每次动手前，先讲再写

1. 用 3-5 句话讲清这一步的背景：它在整个系统里处于什么位置、为什么现在做它。
2. 列出这一步会用到的新概念，**最多 3 条**，每条一句话解释 + 一个生活化比喻。

4. 讲完**停下来**，等我确认后再开始写。

### 写代码时的要求

- 每个新概念第一次出现，在代码里加一行 `# 新手注意：……`，用比喻解释。
- 关键分支、循环、依赖注入的位置加注释说明"在做什么"，不要逐行翻译。
- **单次给出的代码不超过 60 行**。超了就是一次做了太多，拆成两步，
  中间停下来讲一遍再继续。

### 写完必须停下来

- 用 3 句话说明这次的数据怎么流动。
- 明确指出"你最该看懂的是第 a 行到第 b 行"。
- 主动问一句"这里要不要我讲细一点"。
- **等我回复"继续"再动下一步**，不要连续往下做。

### 我提问时的处理顺序

1. 先回答问题，**不要边回答边继续写代码**。
2. 概念类问题用比喻讲，不要贴官方文档原文，也不要堆术语。
3. 回答完后问一句"继续刚才的进度吗"，我确认再往下。
